1 Arquitetura de Software e Decisões de Design

O projeto implementa rigorosamente os princípios SOLID e padrões GoF (Strategy, Factory, Adapter, Facade, Observer) através de contratos estritos definidos com typing.Protocol. Não foram utilizados frameworks web desacoplados como FastAPI; o modelo final é servido de forma nativa e conteinerizada através da abstração mlflow.pyfunc.PythonModel.

🏛️ Contratos Estritos (Protocols)

Toda a comunicação interna obedece a interfaces semânticas independentes de implementação:

  • ModeloPreditor: Inferência tabular unificada
  • MotorTreino: Validação cruzada e tuning
  • MotorTabela: Vetorização Pandas / Polars
  • FonteDados: Ingestão polimórfica
  • ObservadorMLflow: Padrão Observer de publicação

⚡ Tipagem Pura sem "object"

Em conformidade com as regras de governança, o tipo object e typing.Any foram totalmente extintos. Foram criados Type Aliases semânticos recursivos (PEP 695) como ValorConfiguracao, ValorMetricaParametro e ValorResultadoPipeline.

🛡️ Trilha de Motores Isolados

O framework PyCaret utiliza exclusivamente suas chamadas nativas de alta performance (RegressionExperiment). A trilha Scikit-Learn opera de forma 100% independente com Pipeline, ColumnTransformer e buscas dedicadas (Grid, Random, Halving).

2 Catálogo Completo dos Padrões de Projeto GoF (Gang of Four)

Para garantir manutenibilidade corporativa, desacoplamento rigoroso e testabilidade em nível de produto, a arquitetura do sistema adota de forma intencional os padrões consagrados do Gang of Four (GoF). 2.1 Padrões Criacionais: Fábricas e Instanciação Desacoplada

Os padrões criacionais abstraem o processo de instanciação de objetos, garantindo que o sistema seja independente de como seus componentes são criados, compostos e representados. No projeto, a configuração do arquivo configuracoes/projeto.yaml dita quais classes são instanciadas sem que haja dependência direta entre módulos.

🏭 FabricaFontes

Localização: app/fontes_dados/fabrica_fontes.py
Inspeciona a chave fonte_dados.tipo e instancia dinamicamente o adaptador correspondente (FonteExcel, FonteSql ou FonteApi).

  • Entrada: Dicionário de configuração YAML
  • Saída: Instância compatível com FonteDados
  • Vantagem: Alternar de planilha Excel para API REST sem alterar o código de ingestão.

⚙️ FabricaMotores

Localização: app/motores_tabela/fabrica_motores.py
Instancia a engine tabular configurada em motor_tabela.tipo, retornando polimorficamente MotorPandas ou MotorPolars.

  • Entrada: String identificadora ("pandas" ou "polars")
  • Saída: Instância compatível com MotorTabela
  • Vantagem: Transição transparente entre processamento em memória e lazy execution em Rust.

🗳️ FabricaVotacao

Localização: app/modelos_votacao/fabrica_votacao.py
Instancia o regressor de ensemble configurado em modelagem.ensemble.tecnica_votacao, integrando os estimadores treinados sob a estratégia escolhida.

  • Suporte: 7 técnicas de consenso matemático
  • Saída: Instância compatível com ModeloPreditor
  • Vantagem: Criação sob demanda de comitês de decisão heterogêneos.
Exemplo de Código: Factory Method em FabricaFontes Python 3.12+ 
class FabricaFontes:
    """Fábrica de instâncias de fontes de dados conforme especificação YAML."""

    @staticmethod
    def criar_fonte(configuracao: dict[str, Any]) -> FonteDados:
        tipo = configuracao.get("tipo", "excel").lower()
        match tipo:
            case "excel":
                return FonteExcel(caminho_arquivo=configuracao["caminho"])
            case "sql":
                return FonteSql(url_conexao=configuracao["url_conexao"], consulta=configuracao["query"])
            case "api":
                return FonteApi(endpoint=configuracao["url"], cabecalhos=configuracao.get("headers", {}))
            case _:
                raise ErroConfiguracaoInvalida(f"Tipo de fonte desconhecido: {tipo}")

2.2 Padrões Estruturais: Adaptadores, Fachadas e Composites

Os padrões estruturais tratam de como classes e objetos são compostos para formar estruturas maiores e coesas, preservando a flexibilidade e o baixo acoplamento entre bibliotecas externas e contratos de domínio.

🔌 Adapter: Motores de Treino

Localização: app/motores_treino/motor_sklearn.py e motor_pycaret.py
Scikit-Learn e PyCaret possuem paradigmas e APIs totalmente antagônicas. O PyCaret utiliza uma máquina de estados procedural (RegressionExperiment, setup, create_model, pull), enquanto o Scikit-Learn utiliza pipelines composicionais e estimadores puros.

O padrão Adapter unifica ambos sob a interface MotorTreino (métodos treinar_e_avaliar_cv, ajustar_hiperparametros e finalizar_modelo). O orquestrador não sabe qual biblioteca está executando o treinamento.

📦 Adapter: ModeloServico PyFunc

Localização: app/orquestracao_ml/modelo_servico.py
O MLflow Serving exige que modelos customizados herdem de mlflow.pyfunc.PythonModel e implementem o método predict(context, model_input).

A classe ModeloServico atua como Adapter empacotando o regressor treinado juntamente com o interpretador de regras de negócio AST. A chamada de predição calcula o preço estatístico e aplica todas as regras pós-processadas de forma unificada.

🌳 Composite: RegressorVotacao

Localização: app/modelos_votacao/regressor_votacao.py
Implementa o contrato ModeloPreditor encapsulando internamente uma lista de outros objetos ModeloPreditor (Random Forest, XGBoost, LightGBM, etc.).

Quando o cliente invoca predizer(X), o Composite despacha a predição para todos os componentes individuais e agrega as predições aplicando a técnica de votação configurada, agindo como se fosse um único modelo homogêneo.

🏛️ Facade: MainPipeline

Localização: app/orquestracao_ml/main_pipeline.py
O fluxo completo de Machine Learning envolve coordenar mais de 10 subsistemas especializados: Ingestão de Dados, Staging SQLite, Análise Exploratória (EDA), Particionamento de Folds, Validação Cruzada Pareada dos 10 Modelos, Teste Não-Paramétrico de Friedman, Pós-teste de Nemenyi com Diferença Crítica (CD), Seleção do Campeão ou Ensemble, Tuning Fino de Hiperparâmetros, Diagnóstico de Viés/Variância, Importância de Features, Compilação de Regras AST e Publicação no MLflow Model Registry com notificação a observadores.

O padrão Facade expõe uma interface de nível executivo com métodos claros (executar_pipeline_completo() e executar_apenas_campeao()), blindando a aplicação cliente, a CLI e os scripts de inicialização de lidarem diretamente com as dezenas de dependências internas.

2.3 Padrões Comportamentais: Estratégias, Observadores e Interpretador AST

Os padrões comportamentais concentram-se nos algoritmos, na atribuição de responsabilidades e na dinâmica de comunicação e fluxo de eventos entre os objetos do sistema.

🎯 Strategy (Estratégia Intercambiável)

O padrão Strategy define uma família de algoritmos, encapsula cada um deles em classes isoladas e torna-os mutuamente intercambiáveis em tempo de execução via projeto.yaml:

  • Motores Tabulares: MotorPandas e MotorPolars implementam estratégias de engenharia de atributos e filtragem distintas sob o protocolo MotorTabela.
  • Motores de Treinamento: MotorSklearn e MotorPycaret como estratégias concorrentes de validação e otimização.
  • Estratégias de Validação Cruzada: 5 estratégias de particionamento (kfold, repeated_kfold, stratified_kfold, group_kfold, timeseries_split).
  • Estratégias de Votação (Ensemble): 7 estratégias de combinação matemática (Média Simples, Ponderada por R², Mediana, Rank Average, Trimmed Mean, Stacking e Voting Nativo).

👁️ Observer (Publicador / Assinante)

Implementado no ciclo de publicação do MLflow para desacoplar a entrega do modelo dos efeitos colaterais de governança e monitoramento:

  • Subject: PublicadorServico gerencia inscritos com adicionar_observador() e dispara notificar_publicacao() após cada deploy.
  • Protocol: ObservadorMLflow define o método ao_publicar(evento: EventoPublicacaoMLflow).
  • ObservadorAuditoria: Grava eventos estruturados em formato append-only JSONL imutável para compliance corporativo.
  • ObservadorMetricas: Atualiza métricas e histogramas de latência para telemetria com Prometheus e Grafana.

🛡️ Interpreter (Interpretador de AST Restrita)

Localização: app/regras_negocio/avaliador_regras.py
A governança do projeto proíbe terminantemente chamadas a eval() ou exec() arbitrários. O padrão Interpreter implementa um avaliador seguro que analisa a gramática de expressões sintáticas a partir da árvore abstrata do Python (ast.AST).

Somente nós permitidos por uma lista positiva (allowlist) — como ast.BinOp, ast.UnaryOp, ast.Compare, ast.Constant e ast.Name — são executados. Tentativas de import, abertura de arquivos ou chamadas de sistema resultam em exceção imediata antes de qualquer processamento.

💾 Repository (Isolamento de Persistência SQLite)

Localização: app/repositorios_dados/repositorio_sqlite.py
Embora o SQLite atue exclusivamente como área de staging intermediária, seu acesso é mediado pelo padrão Repository através do contrato RepositorioDados.

A camada analítica interage com métodos orientados a coleção (salvar_tabela, obter_tabela, contar_registros, executar_consulta), permitindo substituir o SQLite por DuckDB, PostgreSQL ou Parquet sem alterar a lógica de negócio.

Implementação do Padrão GoF Observer no Ciclo de Vida do MLflow app/contratos_dados/observador_mlflow.py & app/orquestracao_ml/publicador_servico.py 
from typing import Protocol
from dataclasses import dataclass
from datetime import datetime

@dataclass(frozen=True)
class EventoPublicacaoMLflow:
    """Evento imutável emitido pelo Subject após tentativa de publicação."""
    sucesso: bool
    nome_experimento: str
    nome_modelo_registrado: str
    run_id: str | None
    versao_modelo: str | None
    metadados: dict[str, str | float | int | bool]
    tempo_execucao_segundos: float
    data_hora: datetime
    mensagem_erro: str | None = None

class ObservadorMLflow(Protocol):
    """Contrato Protocol para observadores de eventos de deploy do MLflow."""
    def ao_publicar(self, evento: EventoPublicacaoMLflow) -> None: ...

class PublicadorServico:
    """Subject concreto que gerencia a lista de observadores e dispara notificações."""
    def __init__(self, uri_rastreamento: str | None = None) -> None:
        self._observadores: list[ObservadorMLflow] = []

    def adicionar_observador(self, observador: ObservadorMLflow) -> None:
        self._observadores.append(observador)

    def notificar_publicacao(self, evento: EventoPublicacaoMLflow) -> None:
        for obs in self._observadores:
            obs.ao_publicar(evento)

3 Camada Estatística Independente: Testes de Friedman e Nemenyi

A escolha do modelo campeão não é baseada apenas na média simples de um único fold. Adotamos o protocolo estatístico formal de Janez Demšar (2006), que assegura que o modelo vencedor é significativamente superior aos demais em uma bateria pareada de validação cruzada.

2.1. Teste Não-Paramétrico de Friedman

Compara $k$ algoritmos avaliados sobre $N$ blocos pareados (folds da validação cruzada). Para cada fold $i$, os modelos recebem postos de $1$ (menor erro RMSE) até $k$ (maior erro).

Estatística Qui-Quadrado de Friedman:
χ²_F = [12N / (k * (k + 1))] * [ Σ (R_j)² - (k * (k + 1)²) / 4 ]

Onde $R_j = \frac{1}{N} \sum_{i=1}^N r_i^j$ representa o posto médio do modelo $j$. Se o $p$-valor for inferior ao nível de significância configurado (ex: $\alpha = 0.05$), rejeita-se a hipótese nula de que todos os regressores possuem comportamento idêntico.

2.2. Pós-Teste de Nemenyi e Diferença Crítica (CD)

Após a rejeição de $H_0$ por Friedman, o teste de Nemenyi calcula a Diferença Crítica (CD) para comparações pareadas sem inflacionar o erro Tipo I (falsos positivos):

CD = q_α * sqrt( (k * (k + 1)) / (6 * N) )

Se a diferença entre os postos médios de dois modelos $|R_a - R_b| > CD$, a diferença de performance é estatisticamente significante. O modelo com menor posto médio absoluto é eleito o Modelo Campeão Estatístico.

5 Guia de Expressões Seguras: Pandas & Polars via AST

Para assegurar máxima flexibilidade sem violar a segurança, o sistema oferece suporte a expressões declarativas configuradas no arquivo YAML. O interpretador de AST (Abstract Syntax Tree) restrito compila e executa as expressões diretamente sobre as estruturas colunares dos motores.

Filtros de Registros (Boolean Masking)

Elimina amostras que violam integridade física ou regras de negócio antes do staging:

configuracoes/projeto.yamlFiltros Tabulares
filtros:
  ativo: true
  expressoes:
    # Garante metragens fisicamente válidas
    - nome: metragem_positiva
      ativo: true
      expressao:
        pandas: "df['Metragem'] > 0"
        polars: "pl.col('Metragem') > 0"

    # Preço mínimo de venda realista em Ribeirão Preto
    - nome: preco_minimo_valido
      ativo: true
      expressao:
        pandas: "df['Valor_da_Venda'] >= 50000"
        polars: "pl.col('Valor_da_Venda') >= 50000"

7 Catálogo dos 10 Modelos de Machine Learning

O pipeline suporta 10 algoritmos de regressão configuráveis, disponíveis tanto na trilha Scikit-Learn quanto na trilha PyCaret:

1. Regressão Linear Múltipla

Conceito: Modelo linear clássico por Mínimos Quadrados Ordinários (OLS).

  • Vantagens: Rápido, determinístico e 100% interpretável por coeficientes.
  • Atenção: Sensível a multicolinearidade e não captura efeitos não-lineares.

2. Regressão Lasso (L1)

Conceito: Penalização L1 que zera coeficientes de variáveis irrelevantes.

  • Vantagens: Seleção automática de atributos e redução de ruído.
  • Atenção: Exige padronização das features (StandardScaler).

3. Regressão Ridge (L2)

Conceito: Regularização Tikhonov que mitiga variância reduzindo coeficientes sem zerá-los.

  • Vantagens: Estabilidade superior sob alta correlação entre features.
  • Atenção: Mantém todas as variáveis no modelo.

4. ElasticNet (L1 + L2)

Conceito: Combinação balanceada entre Lasso e Ridge via hiperparâmetro l1_ratio.

  • Vantagens: Seleciona grupos de variáveis correlacionadas com estabilidade.
  • Atenção: Exige busca bidimensional (alpha e l1_ratio).

5. Árvore de Decisão (DecisionTreeRegressor)

Conceito: Particionamento recursivo do espaço amostral minimizando variância do alvo.

  • Vantagens: Captura não-linearidades e interações sem exigir escala.
  • Atenção: Alto risco de overfitting se max_depth não for podado.

6. Floresta Aleatória (RandomForestRegressor)

Conceito: Ensemble de bagging com agregação de múltiplas árvores e feature subspacing.

  • Vantagens: Drástica redução de variância e robustez a ruído e outliers.
  • Atenção: Maior consumo de memória e tempo de inferência.

7. SVR (Support Vector Regression)

Conceito: Encontra um hiperplano com margem epsilon-tube imune a pequenas flutuações.

  • Vantagens: Excelente para conjuntos com alta dimensionalidade (kernel RBF).
  • Atenção: Complexidade de treino $O(n^2)$ a $O(n^3)$.

8. Rede Neural MLP (Multi-Layer Perceptron)

Conceito: Rede neural densa feedforward com retropropagação de erro (Adam).

  • Vantagens: Aproximador universal de funções e padrões intrincados.
  • Atenção: Exige dados escalonados e ajuste de camadas/neurônios.

9. XGBoost (Extreme Gradient Boosting)

Conceito: Boosting com árvores de gradiente de 2ª ordem e regularização formal.

  • Vantagens: Performance competitiva máxima em dados tabulares.
  • Atenção: Requer monitoramento de learning_rate para evitar sobreajuste.

10. LightGBM (Light Gradient Boosted Machine)

Conceito: Gradient boosting baseado em histogramas com crescimento leaf-wise.

  • Vantagens: Velocidade de treino ultrarrápida e baixo consumo de RAM.
  • Atenção: Em bases pequenas pode sobreajustar rapidamente se leaf-wise for profundo.

8 As 7 Técnicas de Votação (Ensemble)

A FabricaVotacao permite combinar as previsões dos $N$ melhores modelos eleitos por Friedman:

Técnica no YAML Mecanismo de Combinação Vantagem Estratégica
media_simples Média aritmética uniforme entre os modelos componentes. Reduz a variância sem custo computacional adicional.
voting_regressor Instância oficial do VotingRegressor do Scikit-Learn. Padrão ouro do ecossistema Scikit-Learn com suporte nativo a pipelines.
media_ponderada_rmse Pesos inversamente proporcionais ao RMSE obtido em CV: $w_i \propto \frac{1}{\text{RMSE}_i}$. Dá maior protagonismo aos modelos que erraram menos na validação.
media_ponderada_postos Pesos decrescentes atribuídos segundo o ranking de Friedman. Ponderação matematicamente robusta que não é distorcida por magnitudes de erro.

stacking Meta-aprendizado via StackingRegressor com meta-modelo (ex: RidgeCV). Aprende a ponderação ótima de combinação através de validação cruzada out-of-fold.

9 Estratégias de Validação Cruzada (Folds): Conceitos e Quando Utilizar

A validação cruzada baseada em folds (partições amostrais) é o alicerce metodológico que garante que as estimativas de performance e a seleção do modelo campeão por Friedman/Nemenyi sejam generalizáveis, imunes a viés de partição e protegidas contra vazamento de dados (data leakage).

O que é um Fold e como funciona o K-Fold?

O conjunto de desenvolvimento é dividido aleatoriamente em $K$ subconjuntos mutualmente exclusivos (folds) de proporções idênticas. O treinamento e teste ocorrem em $K$ iterações cíclicas e pareadas:

  • A cada iteração $k \in \{1, \dots, K\}$, exatamente $K - 1$ folds são combinados para calibrar os parâmetros do modelo (conjunto de treino).
  • O 1 fold restante permanece estritamente oculto e é utilizado para computar o erro de generalização out-of-sample ($RMSE_k$).
  • Ao final das $K$ iterações, toda e qualquer amostra da base foi avaliada exatamente uma vez no papel de teste, gerando a matriz pareada de perdas requerida pelo teste não-paramétrico de Friedman.
RMSE_Médio = (1 / K) * Σ [ RMSE_k ]
Variância da Estimativa (Erro Padrão) = sqrt( (1 / (K - 1)) * Σ (RMSE_k - RMSE_Médio)² )

Guia Definitivo: Quando Utilizar Cada Estratégia de Fold?

A escolha da estratégia de particionamento depende da presença de correlações espaciais (mesmo condomínio), temporais (ciclos de mercado) ou desbalanceamento estrutural de valores:

Estratégia de Fold Quando Deve Ser Usada? Cenário Imobiliário (Ribeirão Preto) Risco de Usar Estratégia Incorreta
K-Fold Padrão
kfold		 Amostras I.I.D. (independentes e identicamente distribuídas), homogêneas e sem forte agrupamento por condomínio ou série temporal. Apartamentos avulsos distribuídos aleatoriamente em bairros distintos. Se houver prédios com múltiplas unidades, causa vazamento de condomínio (data leakage).
Repeated K-Fold
repeated_kfold		 Bases de dados pequenas a médias (500 a 5.000 amostras) para estabilizar a variância do split aleatório. Bases onde pequenas flutuações de partição alteram o vencedor de Friedman. Gera $K \times R$ folds pareados para maior poder estatístico. Custo computacional multiplicado pelo número de repetições ($K \times R$).
Group K-Fold
group_kfold		 Quando existem múltiplas unidades do mesmo condomínio, edifício ou empreendimento. Prédio com 20 apartamentos anunciados. Todas as 20 unidades devem ficar juntas no mesmo fold (ou todas no treino, ou todas no teste). Data Leakage Crítico: O estimador decora particularidades do condomínio gerando métricas perfeitas que colapsam em prédios novos.
Time Series Split
time_series_split		 Quando as transações possuem data e o mercado imobiliário reflete ciclos econômicos (Selic, inflação IPCA, crédito imobiliário). Vendas ocorridas entre 2021 e 2026. O modelo treina no passado (2021-2023) e valida estritamente no futuro (2024-2026). Look-ahead Bias: Usar o futuro para prever o passado produz modelos ilusoriamente bons que falham em produção.
Stratified K-Fold
stratified_kfold		 Distribuição com forte assimetria no valor venal (quantis de preço ou zonas da cidade). Garante que cada fold contenha proporções idênticas de apartamentos populares (econômicos) e de alto padrão (Zona Sul). Folds desbalanceados podem conter apenas imóveis econômicos ou apenas coberturas de luxo, distorcendo o RMSE.
Nested CV
nested_cv		 Quando há otimização de hiperparâmetros (tuning) e seleção de algoritmo simultâneos. Loop Externo avalia a capacidade de generalização real do campeão; Loop Interno executa o Tuning (max_depth, alpha) no treino do fold. Overfitting de Hiperparâmetros: O modelo aparenta baixo erro de validação, mas o hiperparâmetro foi sobredimensionado.

🎯 Diretrizes de Escolha do Número de Folds ($K$)

  • $K = 3$: Pipelines ágeis de desenvolvimento, validação rápida em CI/CD e prototipação com menor custo de CPU.
  • $K = 5$: Padrão industrial equilibrado (80% treino / 20% teste a cada ciclo). Excelente compromisso de estabilidade e tempo.
  • $K = 10$: Recomendação acadêmica clássica para relatórios finais. Minimiza o viés pessimista da estimativa de erro.

10 Diagnóstico de Overfitting vs Underfitting (Viés x Variância)

O módulo DiagnosticoCurva avalia sistematicamente a capacidade de generalização dos modelos, medindo a evolução do erro de treino (viés) e do erro de validação cruzada (variância) conforme a complexidade dos algoritmos varia.

Equação Fundamental de Decomposição do Erro

Erro Total(x) = Viés²(x) + Variância(x) + σ² (Ruído Irredutível)
Gap de Variância: Δ = max(0, RMSE_validacao - RMSE_treino)

À medida que a complexidade aumenta, o Viés decai monotonicamente (o modelo se ajusta com mais facilidade ao treino). A Variância, contudo, se eleva: o erro de validação atinge um ponto ótimo de mínimo global e, a partir de determinado nível, passa a divergir do erro de treino, caracterizando sobreajuste (overfitting).

⚠️ Underfitting (Alto Viés)

O modelo é simples demais para capturar os padrões fundamentais do mercado imobiliário. Ambos os erros de treino e validação são excessivamente altos ($RMSE > 40.000$).

🎯 Generalização Ótima

Equilíbrio ideal entre capacidade e estabilidade. O erro de validação é mínimo, e o gap relativo entre validação e treino permanece rigorosamente contido ($Gap \le 20\%$).

🔥 Overfitting (Alta Variância)

O modelo memoriza ruídos do conjunto de treinamento. O erro de treino torna-se artificialmente baixo, enquanto o erro de validação explode ($Gap > 20\%$).

Hiperparâmetros de Complexidade Mapeados por Família de Modelo

O sistema infere automaticamente o hiperparâmetro de complexidade adequado de acordo com o modelo selecionado, aceitando também parâmetros explícitos:

Modelo Hiperparâmetro Dinâmico Comportamento sob Variação de Complexidade
random_forest, arvore_decisao, xgboost, lightgbm max_depth Controla a profundidade máxima de corte das árvores; maiores valores aumentam variância.
ridge, lasso, elasticnet alpha Regularização da magnitude dos pesos; menores valores de alpha permitem modelos mais livres.
regressao_linear fit_intercept Ajuste de intercepto e liberdade do hiperplano multidimensional.
svr C Penalização de desvios além da margem $\epsilon$; maior C força ajuste mais rigoroso.
rede_neural hidden_layer_sizes Número e dimensão das camadas densas ocultas do perceptron multicamadas.
modelo_campeao auto (Dinâmico) Detecta dinamicamente o hiperparâmetro do modelo campeão eleito ou configurado (ex: hidden_layer_sizes (campeão) se rede neural, alpha (campeão) se ridge/lasso, C (campeão) se svr, max_depth (campeão) se arvore/floresta).

Utilizado para modelos baseados em árvore (Random Forest, Árvore de Decisão, XGBoost e LightGBM). Mensura a redução média de impureza (variância do erro quadrático) agregada em todos os nós da floresta.

  • Executa Teste Não-Paramétrico de Friedman e Pós-Hoc de Nemenyi / Wilcoxon pareado.
  • Ajusta hiperparâmetros (Tuning Random / Bayesian) ou monta Ensemble de Votação (7 técnicas).
  • Treina o vencedor na base completa e congela os artefatos de avaliação.
  • Registra métricas, postos, curvas de complexidade e modelo no MLflow.

🐳 Recarregamento Automático e Compatibilidade Multi-Ambiente

O script foi desenhado com inteligência de infraestrutura para operar perfeitamente em dois cenários:

Cenário A: Stack Docker Compose em Execução

Se o container mlflow-serving for detectado no Docker, o script:

  • Publica a nova versão do modelo no Model Registry conectado ao PostgreSQL e RustFS.
  • Executa o recarregamento do container (docker restart mlflow-serving).
  • Garante que a porta 8080 não sofra conflito de socket.

  • mlflow models serve -m "models:/previsao_preco_imoveis/latest" -p 8080 -h 0.0.0.0 --no-conda
  • Fica ativo e monitora interrupções (Ctrl+C).

👁️ Padrão GoF Observer no MLflow (Governança & Métricas Desacopladas)

GoF Behavioral Pattern

Para garantir total desacoplamento entre o registro de modelos no MLflow e as ações secundárias de auditoria, métricas e alertas, foi implementado o padrão GoF Observer com contratos estritos via typing.Protocol:

1. Subject (PublicadorServico)

Atua como o Subject que gerencia os observadores inscritos via adicionar_observador() e remover_observador(). Ao finalizar o registro ou ao detectar falhas, dispara _notificar_observadores(evento) de forma resiliente.

2. ObservadorAuditoria (JSONL)

Grava automaticamente logs estruturados de governança em storage-data/auditoria_mlflow.jsonl, contendo timestamp_iso, run_id, model_uri, modelo_campeao, modo_execucao e tags de compliance.

3. ObservadorMetricas (Prometheus)

Calcula contadores em tempo real (mlflow_publicacao_sucesso_total, mlflow_publicacao_falha_total) e exporta metadados em storage-data/metricas_mlflow.prom para consumo pelo Prometheus e Grafana.

Exemplo de Uso no Pipeline Python:

from app.orquestracao_ml.publicador_servico import PublicadorServico
from app.orquestracao_ml.observador_auditoria import ObservadorAuditoria
from app.orquestracao_ml.observador_metricas import ObservadorMetricas

# 1. Instancia o Subject com o tracking URI do MLflow
publicador = PublicadorServico(tracking_uri="http://localhost:5000")

# 2. Conecta os Observers desacoplados
publicador.adicionar_observador(ObservadorAuditoria())
publicador.adicionar_observador(ObservadorMetricas())

# 3. Publica o modelo — todos os observadores são notificados automaticamente!
publicador.publicar_modelo_servico(
    modelo_servico=servico,
    experimento="imoveis_regressao",
    nome_modelo_registrado="previsao_preco_imoveis",
    tags={"modelo_campeao": "random_forest", "modo_execucao": "apenas_campeao"}
)
